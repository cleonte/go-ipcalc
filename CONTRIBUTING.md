# Contributing

go-ipcalc is a Go port of [ipcalc](https://gitlab.com/ipcalc/ipcalc) and aims
to behave byte-for-byte like it. Behavior questions are settled by the
upstream C implementation and by `doc/requirements/`.

## Workflow

For any change that alters observable behavior, work in this order:

1. Update (or add) the requirement in `doc/requirements/`.
2. Write the test the requirement's acceptance criteria imply.
3. Change the code.

Keep `internal/ipcalc/cli.go` `usage()`, `man/ipcalc.1.md` and `NEWS` in step
with the code. See `AGENTS.md` for the details.

## Build and test

```sh
go build ./...
go test -race ./...
go vet ./...
golangci-lint run ./...
go generate ./... && git diff --exit-code   # man page and test tables are generated
```

`golangci-lint` v2 must be installed separately (see
<https://golangci-lint.run/welcome/install/>); its configuration is
`.golangci.yml`. CI runs the same checks on Linux, Windows and macOS. Everything is plain Go; no C
compiler, Python or Perl is needed. New cases go in the table in
`internal/ipcalc/` with an expected-output file in `testdata/`.

## Generated test tables

`internal/ipcalc/cases_gen_test.go`, `debian_cases_gen_test.go` and
`color_cases_gen_test.go` are written by `internal/ipcalc/internal/gencases`
(run by `go generate ./...`); do not edit them by hand. The inputs are
committed: `testdata/upstream/meson-tests.json` is a snapshot of the upstream
test list, and `testdata/color-cases.json` lists the color cases.

To follow a newer upstream, in the C ipcalc repository run

```sh
meson setup build && meson introspect --tests build > meson-tests.json
```

then replace the absolute paths in it by placeholders (`@BUILD@` for the
build directory, `@SRC@` for the source directory, so that no local paths are
committed), copy the file to `internal/ipcalc/testdata/upstream/meson-tests.json`,
copy any new expected-output files from the C `tests/` directory to
`internal/ipcalc/testdata/`, and run `go generate ./...`.

## Merge requests

Issues and merge requests go to <https://gitlab.com/ipcalc/go-ipcalc>; the
GitHub repository is a read-only mirror. The GitLab pipeline
(`.gitlab-ci.yml`) must pass. Dependency updates come from Renovate
(`renovate.json`), which needs the Mend Renovate app enabled for the GitLab
project.

## Commits

* One logical change per commit, with a message describing what changed.
* Sign off every commit (`git commit -s`): by doing so you certify the
  [Developer Certificate of Origin](https://developercertificate.org/).
* New source files carry the SPDX/GPL-2.0 header used by the existing ones.
* Contributions are licensed GPL-2.0-only, like the rest of the project.

Behavior that is wrong in upstream ipcalc as well should be reported there
first; this port tracks upstream.

## Releasing

1. Add a `* go-ipcalc X.Y.Z (released DATE)` section to `NEWS`; it becomes the
   release notes.
2. Tag and push: `git tag -a vX.Y.Z -m "go-ipcalc X.Y.Z" && git push origin vX.Y.Z`.

The `release` job of the GitLab pipeline runs GoReleaser (`.goreleaser.yaml`):
it builds the archives and the Linux packages (`.deb`, `.rpm`, `.apk`, package
`go-ipcalc`), writes `SHA256SUMS`, uploads them to the project's package
registry and publishes the GitLab release with the NEWS entry as its notes.
It authenticates with the job token (`gitlab_urls.use_job_token`), so no
token is needed for it. SLSA provenance metadata is generated by the runner
(`RUNNER_GENERATE_ARTIFACTS_METADATA`). The `homebrew` job then updates the
formula in the GitHub repository `cleonte/homebrew-tap`
(`brew install cleonte/tap/go-ipcalc`) from `packaging/homebrew/`.

One-time project settings:

* Protect the tag pattern `v*` (Settings, Repository, Protected tags), so that
  only maintainers can release and protected variables are available to the
  tag pipeline.
* Add the CI/CD variable `HOMEBREW_TAP_TOKEN` (masked, protected): a GitHub
  token that can push to the tap only. Without it the `homebrew` job is
  skipped and the formula must be updated by hand with
  `packaging/homebrew/render.sh VERSION SHA256SUMS`.
* If the job token cannot create releases on your GitLab instance, add a
  masked, protected `GITLAB_TOKEN` variable (a project access token with the
  `api` scope and the Maintainer role) and remove `GITLAB_TOKEN: $CI_JOB_TOKEN`
  from the `release` job and `use_job_token` from `.goreleaser.yaml`.

To try a release locally without publishing, run
`goreleaser release --snapshot --clean` (the result is in `dist/`).
